# Amplitude developer guide

This document explains what Amplitude is, how it is built, and how the code
works, so that someone new can continue the work. `USAGE.md` is the user
manual; this file is for people changing the code.

## 1. Goals and constraints

Amplitude is a music player in the style of WinAmp 2: three small windows
(main, equaliser, playlist), classic `.wsz` skin support, and its own
original look. The constraints below explain most design decisions.

- **Small.** One executable of about 1 MB (Linux) or 1.25 MB (Windows) with
  every decoder compiled in. No GUI toolkit, no runtime dependencies beyond the operating system.
- **Portable.** Linux (X11) and Windows today; macOS is intended. All
  platform code sits behind one header.
- **Legacy Windows.** The Windows build should run on XP and, ideally, 98.
  That rules out newer DLLs and newer struct sizes, and means every
  wide-character ("W") call needs an ANSI fallback. See section 9.
- **Legally distinct.** No WinAmp name, logo or artwork is shipped. The
  built-in skin is original and generated by code. Third-party skins are
  loaded if the user supplies them, never bundled.
- **Plain C (gnu99), GPL 3 or later.**

## 2. Status

Working and tested on Linux:

- Playback of MP3, FLAC, WAV, Ogg Vorbis, Opus, AAC (MP4/M4A and ADTS),
  MOD/XM/S3M/IT, with gapless track changes
- Main window, equaliser (10 bands, presets, genre-based AUTO), resizable
  playlist with multi-select, jump-to-file search, right-click menu
- Classic skin loading, built-in resolution-independent skin, Unicode titles
- Tags (ID3v1/v2, Vorbis comments, MP4, module names)
- Drag and drop, folder adding, single instance, saved settings and playlist
- `.deb` package with icon and desktop entry

**Windows 11 has been tested twice**, by script. On 4 October 2026: start-up,
Unicode file names, every format, drawing at four sizes, menus on two
monitors, playlist commands, settings, single instance, CPU and handle use
all passed with no change to the player. On 8 October 2026, for 0.2.0:
several files opened at once, media keys, streams of every kind over
Winsock and WinINet, the Open location window, and CDs as far as a disc
image goes; one fault was found and fixed (a web address given on the
command line was turned into a file path). `docs/WINDOWS_TESTING.md` holds
the plan and the results. Not yet covered there: a real CD in a drive, the
installers, the file dialogs and drag and drop, a real classic skin, sound
judged by ear, and the release executables themselves (the tests used
builds made on Windows with another compiler). **Windows XP and 98 have not
been tested**; that is the most valuable next step. Section 12 lists what
is missing.

## 3. Building

    make            # build/linux/amplitude
    make windows    # build/win32/amplitude.exe (32-bit, for every Windows)
                    # and build/win64/amplitude.exe (64-bit)
    make windows32  # only the 32-bit one
    make windows64  # only the 64-bit one
    make installer  # build/amplitude-<version>-win32-setup.exe and -win64-setup.exe
    make all        # Linux, the .deb and .rpm, both Windows builds and the installers
    make dist       # build/dist/: installers, .deb, .rpm, portable zips, source tarball
    make deb        # build/amplitude_<version>_<arch>.deb
    make rpm        # build/amplitude-<version>-1.<arch>.rpm
    make test       # unit tests (section 10)
    make test-gui   # end-to-end test of the real player; needs an X display
    make fonts      # regenerate src/font_data.c
    make clean

The Linux build needs only `gcc` and `make`. Nothing is downloaded at build
time: the third-party sources, the X11 headers, the font sources and the
test media are all in the tree. The program links against `libX11.so.6`
directly (`-l:libX11.so.6`), so `libx11-dev` is not required; see
`third_party/x11/SOURCE.md`.

The Windows builds need the MinGW-w64 cross-compiler (i686 for `make
windows32`, x86_64 for `make windows64`). If the `mingw-w64` package is
installed, that is used. Otherwise the first build runs
`tools/local-mingw.sh` for the architecture it needs, which downloads the
Debian packages and unpacks them into `.toolchain/` (ignored by git, kept by
`make clean`) without root; this is the one step that needs the network.
Later builds reuse it. Both builds compile the same sources; the legacy
rules in section 9 are about the 32-bit one.

`make installer` builds two NSIS setup programs from one script
(`packaging/installer.nsi`, compiled with `BITS` set to 32 and to 64), one
per build of the player. The 64-bit one refuses to run on 32-bit Windows.
Each adds a Start menu shortcut
(and optionally a desktop one), and registers an uninstaller. An optional
component associates the audio extensions with the player; the comment at
the top of that part of the script explains the three registry mechanisms
it uses, and the extension list there must be kept in step with
`is_audio_file()` in `src/main.c`. It is built as
an ANSI installer (`Unicode false`) because only those start on Windows
95/98/ME. Settings live in Application Data, so the uninstaller leaves them
alone. `makensis` is taken from the system or fetched by
`tools/local-nsis.sh`, like the compiler.

Do not pass `LDFLAGS=...` on the `make` command line for a release build: it
replaces the Makefile's own linker flags, and the executable then comes out
unstripped and about 40% larger.

The build is a single `Makefile`. One `PLATFORM_RULES` template is
instantiated for each platform, so every object is built per platform under
`build/linux/` or `build/win32/`. Third-party objects go under `tp/` and are
compiled with their own flags and with warnings off; our own sources use
`-Wall -Wextra` and are expected to stay warning-free.

Two flags matter for size: `-ffunction-sections` with `--gc-sections` drops
unused code. `-fdata-sections` is used on Linux only, because on Windows
(PE) targets it moves zero-initialised data into the file and bloats it.

- Only `platform_*.c` may include OS headers. Everything else is portable C.

## 5. How rendering works

### Logical and real pixels

All layout is in **logical pixels**: the fixed coordinates of the classic
275x116 layout. The windows are shown at a **scale in percent** (100 to
400), and a logical length `v` is `(v * scale + 50) / 100` real pixels. This
formula exists as `GFX_SCALED` and `PLAT_SCALED`; both sides must use it so
window sizes agree to the pixel.

A `Canvas` (`gfx.h`) wraps a real-resolution framebuffer and carries the
scale, a logical origin offset and a clip rectangle. Every primitive takes
logical coordinates and maps them itself:

- `gfx_rect` rounds both edges through the same mapping, so shapes that
  touch in logical space touch on screen, with no gaps.
- `gfx_hline`, `gfx_vline` and `gfx_bevel` draw one-pixel lines with an even
  real thickness (`round(scale)`), which a scaled 1-pixel rectangle cannot
  guarantee.
- `gfx_triangle` and `gfx_polyline` take fractional coordinates and are
  rasterised in real space (the polyline is anti-aliased; it draws the logo).
- `gfx_blit` copies a region of a bitmap, replicating pixels at whole scales
  and averaging by area at fractional ones.

### Text

There are two text functions.

- `gfx_utext` draws UTF-8 titles. The caller names a design font
  (`font_small` = 5x7, `font_list` = 6x10); the function picks, from four
  embedded sizes (5x7, 6x10, 7x13, 9x15, 10x20), the one that best fits the
  scaled height. A font at its own size is preferred, as long as it reaches
  about two thirds of the height wanted; only beyond that (above roughly
  300%) is a smaller font magnified by a whole factor, which looks blocky.
  Text is therefore always made of whole pixels. `gfx_utext_width` returns the logical width for a given scale.
- `gfx_text` draws the chunky uppercase label font of the built-in skin. It
  is used as drawn at 100% only; at any other scale one of the embedded
  fonts stands in, matched on capital height and set in the same 6-pixel
  cells.

A character without a glyph falls back to its unaccented letter
(`gfx_unaccent`), then to a placeholder. The fonts cover Latin, Greek and
Cyrillic; there is no CJK, Arabic or right-to-left support.

### Skins

A skin (`skin.h`) is a set of **sheets** in the classic layout: `main`,
`titlebar`, `cbuttons`, `numbers`, `playpaus`, `text`, `monoster`, `posbar`,
`volume`, `balance`, `shufrep`, `eqmain`, `pledit`. UI code never draws a
bitmap directly; it calls

    skin_blit(canvas, skin, sheet, sx, sy, w, h, dx, dy)

which means "draw the w*h sprite found at (sx, sy) in this sheet at
(dx, dy)". Each sheet is one of two kinds:

- **Classic**: a bitmap loaded from the `.wsz`. `skin_blit` calls `gfx_blit`.
- **Built-in**: no bitmap. `skin_blit` shifts the canvas origin so that
  sheet position (sx, sy) lands on (dx, dy), clips to the sprite, and runs
  that sheet's painter function in `skin_default.c`. The painter draws the
  whole sheet with ordinary primitives; everything outside the sprite is
  clipped away. Because it draws straight onto the window, the result is at
  real resolution and sharp at any scale.

Running a painter for every sprite of every frame is far too slow (it cost
13% of a CPU core while playing at 150%), so `skin_blit` remembers the
pixels of each built-in sprite the first time and copies them afterwards.
At fractional scales the same sprite can differ by a pixel depending on
where it lands, so an entry is keyed by sheet, source rectangle and the
position's sub-pixel remainder; the comment above the cache in `skin.c`
explains why that is enough. The cache is dropped when the scale or colour
changes, is bounded (`CACHE_MAX_PIXELS`), and a sprite that the caller's
clip cuts into is simply painted. A painter must therefore fill its whole
sheet and not depend on what is underneath. `tests/test_render.c` checks at
every scale that cached frames equal freshly painted ones.

A classic skin may lack sheets; each missing one stays built-in. To change
the built-in look, edit the `paint_*` functions in `skin_default.c`.

Its colours come in two groups. The neutral greys of the window body are
the `COL_*` constants in `theme.h`, shared by everything drawn in the
built-in look. Everything coloured goes
through `theme.c`: the user picks one base colour (menu presets in
`theme_presets`, or `color=` in the settings file) and `theme_set` derives
the related shades from it (dim, peak, display background, grid,
highlight, and the "on" label colour). The `COL_*` macros for those read
the current theme at draw time, so a change shows at once; `set_color` in
`main.c` also rebuilds the skin, because the skin struct caches a few
colours. The menu and the jump window use the same theme.

Loading a `.wsz` (`skin.c`) uses our own ZIP reader and inflate (`zip.c`)
and BMP decoder (1/4/8/16/24/32-bit, RLE4/RLE8). It also reads
`viscolor.txt` and `pledit.txt`, and derives a text colour from `text.bmp`
for titles drawn with our own fonts. All parsers are bounds-checked and
tolerate truncated files.

### Windows and models

Each window has a draw function taking a framebuffer, the scale, the skin
and a model struct, and a hit function returning a `UI_*` element id
(`ui.h`). Ids are unique across windows. The menu, the jump window and the
About window use fixed built-in colours and ignore the skin; the two small
windows share their frame and title bar (`ui_dialog.c`).

Drawing and showing are both skipped when nothing changed. `render()` in
`main.c` draws the equaliser and playlist only when their model differs
from the one last drawn (the playlist model carries `playlist_revision()`,
which counts every change to the list) or the window's `redraw` flag is
set, which happens when it is shown, uncovered or resized and when the
skin, colour or scale changes. So anything a draw function reads must be
in its model, or the window will not update. `plat_window_present` keeps
a copy of the last frame and sends only the rows that differ, so the main
window, which is drawn every frame for the visualiser, pushes just the
display area to the screen.

## 6. How `main.c` works

- **Windows.** `wins[]` holds the four windows (main, equaliser, playlist,
  jump) with logical size, real screen position and visibility. A hidden
  window keeps its offset from the main window (`rel_x`, `rel_y`).
- **Main loop.** Drain platform events, handle a gapless advance or the end
  of the playlist, refresh the gapless queue if needed, draw every visible
  window, then wait up to 33 ms (playing or interacting) or 250 ms (idle).
- **Input.** `handle_event` turns a mouse press into a `pressed` element.
  `track_mouse` applies drags (window move, sliders, resize). On release, if
  the pointer is still on the pressed element, `do_action` runs it. Menu
  commands share `do_action`, so their ids start at 1000.
- **Docking.** Dragging snaps a window to others within 10 pixels. Dragging
  the main window moves every window that touches it, directly or through
  another.
- **Scale changes** (`set_scale`) destroy and recreate all windows at the
  new size and restore the layout from logical offsets.
- **Menus.** `open_menu` fills `menu_items` for one of several lists (main,
  skins, sizes, presets, add) and creates a popup window; `menu_command`
  handles the choice.
- **Adding.** `add_path` accepts a file, an `.m3u`, a folder (recursive,
  sorted, audio files only) or a `.wsz` (which switches skin instead).
- **Gapless queue.** After any change that affects what plays next,
  `queue_dirty` is set and `update_queue` asks the audio engine to open the
  next track in advance.

## 7. How audio works

`audio.c` opens one miniaudio playback device fixed at 44.1 kHz, 16-bit
stereo. Each file is opened through `ma_decoder`, which converts whatever
the source is to that format.

- **Threads.** miniaudio calls `data_callback` on its own thread. One mutex
  guards all shared state. Decoders are opened and closed only on the main
  thread.
- **Gapless.** There are two decoder slots. `audio_queue_next` opens the
  next file into the idle slot. When the current decoder runs out
  mid-buffer, the callback switches slots and fills the rest of the buffer
  from the new one, then sets `advanced`. The main thread notices with
  `audio_take_advanced`. `audio_queue_next` returns -1 while an advance is
  waiting to be noticed, so the two sides cannot disagree about which track
  is playing.
- **Equaliser.** Ten peaking biquads (RBJ cookbook) per channel plus a
  preamp, applied in the callback.
- **Visualiser.** The callback keeps the last 512 mono samples;
  `audio_get_vis` copies them out. `ui.c` computes the FFT for the spectrum.
- **Extra decoders.** `codec.h` defines a small interface (read, seek,
  close, length). `codec.c` picks a decoder from the file's first bytes or
  extension. `audio.c` wraps the result as a miniaudio custom backend, which
  miniaudio tries before its built-in WAV/FLAC/MP3.

## 8. Other modules

- **`tags.c`** reads only the header bytes it needs, without the decoders.
  All text is converted to UTF-8 (`text_to_utf8`), which is the internal
  encoding everywhere.
- **`playlist.c`** owns the track array (path, title, length, selected flag)
  and reads and writes plain M3U.
- **`stream.c`** fetches audio over HTTP: internet radio and files on web
  servers. `stream_open` starts a thread that connects, follows redirects
  and station playlist files, strips the stations' in-band metadata ("ICY")
  and fills a ring buffer; nothing in it blocks the caller. The connections
  themselves come from the platform (`net_posix.c`, `net_win32.c`), which is
  also where TLS lives: OpenSSL loaded with `dlopen` on Linux, WinINet for
  whole `https` addresses on Windows, both only when first needed, so
  neither is a build or start-up requirement. In `audio.c` a stream fills a
  decoder slot like a file, with three differences: `audio_open` returns at
  once and `audio_update` (called every frame) sets the decoder up when
  enough has arrived, reporting failure through `audio_take_failed`; the
  audio thread decodes only while the buffer holds enough, so it never
  waits for the network; and there is no length, seeking or gapless
  hand-over. miniaudio's own decoders (MP3, FLAC, WAV) read from a stream
  through its usual callbacks. Three of our codecs have a second way in
  that takes a `CodecFeed` function instead of a path:
  `codec_open_aac_stream` finds its way to a frame boundary and decodes
  ADTS frames as they come; `codec_open_vorbis_stream` uses stb_vorbis's
  push interface and follows the Ogg pages itself, so as to restart the
  decoder when a station begins a new logical stream for the next song;
  `codec_open_opus_stream` leaves that to opusfile. The Ogg ones report
  the song from the stream's comments through `Codec.take_title`. Which
  decoder a stream gets is decided in `stream_kind` (audio.c) from its
  first bytes and its content type. HLS is handled entirely in `stream.c`
  (`hls_run`): it fetches playlist and segments, takes the audio out of
  transport stream packets or MP4 fragments where needed (giving each AAC
  frame from an MP4 the ADTS header it lacks there), and writes it to the
  same buffer, so the decoders see ordinary AAC or MP3. A whole `.m4a`
  file on the web is another matter: minimp4 wants to seek in it, so it
  does not play. `tests/test_stream.c` runs all of this against
  `tests/stream_server.py`.
- **`cd.c`** knows audio CDs: the track list of a disc and its raw
  sectors. The drive itself is the platform's (`cd_linux.c` uses the
  kernel's CD-ROM ioctls, `cd_win32.c` opens `\\.\D:` and uses
  `DeviceIoControl`, which needs nothing beyond kernel32 but exists only on
  the NT line; on Windows 9x it sends SCSI commands through ASPI instead,
  loading `wnaspi32.dll` on first use). A track is written as a path, `cdda://<device>/<number>`,
  and from there on is a file like any other: `codec_open` hands such
  paths to `codec_cd.c`, whose reader thread keeps four seconds read
  ahead so that the audio thread never waits for the drive. Instead of a
  device the path may name a CUE sheet with one raw `.bin` file; `cd.c`
  reads those itself. That is a small feature in its own right, and it is
  how everything but the two drive files is tested without a drive
  (`tests/test_cd.c` makes such an image). **`cdnames.c`** finds the
  song names on a thread of its own. First it asks the disc
  (`cd_read_names`: CD-Text, fetched from the drive with one more command
  on each platform and decoded by `cd_text_parse`; or the TITLE and
  PERFORMER lines of an image's sheet). Failing that it works out the disc IDs from the
  track positions and asks MusicBrainz (JSON, read by a few small `js_*`
  functions) and then gnudb (the old CDDB protocol over HTTP). gnudb only
  answers programs whose author has registered an e-mail address, which
  goes into `GNUDB_CONTACT`; while that is empty gnudb is not asked. Both
  are fetched with `stream_fetch`. The player asks when a disc is added
  and when a still nameless CD track starts, unless `cd_names=0`.
- **`mpris.c`** (Linux) answers the desktop's media controls. Modern
  desktops own the media keys and pass them to players over D-Bus, so this
  is what makes keyboard media keys and Bluetooth headphone buttons work.
  libdbus is loaded with `dlopen` when the player starts and its few
  functions are declared by hand, so it is neither a build nor a hard
  run-time dependency. `platform_x11.c` polls it with the X connection and
  turns requests into `PK_MEDIA_*` key events for the main window. Without
  a session bus it grabs the XF86Audio keys from the X server instead; it
  never does both, or each press would count twice. On Windows the same
  key events come from `RegisterHotKey` and `WM_APPCOMMAND`.
- **`config.c`** reads and writes `amplitude.ini` as `key=value` lines of
  integers. Window offsets are stored in logical pixels.
- **`presets.c`** holds the equaliser presets and maps a genre tag to one.
- **Platform layer.** `platform.h` documents every function. Points worth
  knowing:
  - Events carry logical window coordinates and real screen coordinates.
  - `PEV_FILE` delivers dropped files and files sent by a second instance.
  - A popup grabs the mouse so that clicks outside it are reported to it.
  - Single instance on X11 uses a selection whose name includes a hash of
    the settings directory, so a different `XDG_CONFIG_HOME` gives a
    separate player. On Windows it finds the main window by title.
  - X11 window positions come from `ConfigureNotify`, not from querying the
    server, because the window manager applies moves asynchronously.
  - X11 file dialogs shell out to `zenity` or `kdialog`.

## 9. Rules for the Windows build

To keep the executable loadable on Windows 9x and XP:

- **File names are UTF-8 inside the program, always.** Portable code opens
  files only with `plat_fopen`, never `fopen`. In `platform_win32.c` every
  function that takes or returns a path has two branches, chosen by
  `unicode_os()`: on NT-based Windows it converts to UTF-16 and calls the
  wide ("W") function, so any Unicode name works; on Windows 9x it converts
  to the system code page and calls the ANSI ("A") function. The command
  line is re-read as UTF-8 by `plat_args`.
- Wide functions in `kernel32` and the C runtime can be called directly
  (9x has them as stubs that fail). Wide functions in `shell32` and
  `comdlg32` must be fetched with the `optional()` helper, because old
  versions of those DLLs lack them and a missing import stops the program
  from starting.
- UTF-8 conversion is done by hand (`utf8_to_wide`, `wide_to_utf8`):
  Windows 95 has no UTF-8 code page.
- Windows and messages use the ANSI functions. One consequence: text typed
  into the jump-to-file box is limited to the system code page.
- Do not link new DLLs. Anything newer than Windows 95 must be looked up at
  run time with `GetProcAddress` (see `SetProcessDPIAware` in `plat_init`).
- Use old struct sizes where Windows checks them (see
  `OPENFILENAME_SIZE_VERSION_400A`).
- Check the import list after changes:
  `i686-w64-mingw32-objdump -p build/win32/amplitude.exe | grep "DLL Name"`
  should show only KERNEL32, USER32, GDI32, COMDLG32, SHELL32 and msvcrt.

## 10. Testing

    make test       # under 10 seconds once built
    make test-gui   # about 20 seconds; opens real windows

### Unit tests (`make test`)

Each `tests/test_*.c` is a standalone program that links the whole portable
code base (everything except `main.c` and the platform layer), built with
the address and undefined-behaviour sanitizers. `tests/test.h` provides the
`CHECK` macros, a scratch directory, and generators for WAV files and a
small tracker module, so most inputs are created by the tests themselves.

| Test | What it covers |
|---|---|
| `test_gfx` | coordinate mapping at ten scales (no gaps between touching shapes, even line thickness), clipping of every primitive, text widths, whole-factor blits |
| `test_data` | settings round trip and bad input, playlist operations and M3U, preset and genre matching |
| `test_tags` | hand-assembled files for ID3v1, ID3v2.2/2.3/2.4, FLAC, Ogg Vorbis, Opus and MP4; text encodings; 1500 corrupted and truncated files |
| `test_skin` | the ZIP reader and inflate against known deflate streams, BMP decoding in six pixel formats, `viscolor.txt` and `pledit.txt`, damaged archives |
| `test_render` | draws every window and the menu at nine scales and checks that every pixel is written and none outside the buffer; hit testing of the controls |
| `test_codecs` | Opus, Vorbis, AAC (MP4 and ADTS) and module decoding: format, length, full decode, seeking; rejection of junk |
| `test_audio` | the playback engine: every format's length, play/pause/seek/finish, the equaliser path, and gapless hand-over measured by total playing time |

`test_audio` opens the sound device and plays for a few seconds at zero
volume. `test_render` takes a directory as a second argument and then also
saves every image as a PPM file, which is the quickest way to see what a
drawing change did at several scales:

    build/test/test_render tests/media /tmp/renders

`tests/media/` holds six tiny sample files from the web-platform-tests
project (3-clause BSD; see the README there). `tests/inflate_vectors.h` was
generated once with zlib; the recipe is at the top of `test_skin.c`.

### End-to-end test (`make test-gui`)

`tests/gui_test.sh` starts the real player with scratch settings and drives
it with `tests/drive.c`, which sends synthetic X11 key, mouse and
drag-and-drop events and checks window sizes and positions. Afterwards the
script inspects the saved `amplitude.ini` and playlist. It covers folder
adding, docking and group dragging, playlist resizing and multi-select
removal, the menus, presets, drag and drop, jump to file, single-instance
hand-over, restoring everything after a restart, and changing size while
running. The player is given digital silence, so nothing is heard.

Two safeguards matter, because the player is single-instance:

- The test player gets its own `XDG_CONFIG_HOME`. That keeps it away from
  the real settings and makes it a separate instance from a player the user
  may have open.
- `drive` requires `DRIVE_PID` and only touches windows whose `_NET_WM_PID`
  is that process.

Follow the same two rules in any new test that starts the player.

### Not covered

- Windows has no automated test in the build. It is tested by following
  `docs/WINDOWS_TESTING.md` on a Windows machine with the PowerShell helper
  `tests/windows/wintest.ps1`; that document records what the last run
  covered and what it left out (installers, dialogs, skins, XP and 98).
- The real file dialogs (the GUI test substitutes a fake `zenity`).
- Classic skins beyond the generated one in `test_skin`; rendering real
  `.wsz` files is a manual check, since none can be bundled.
- Sound quality: the tests measure timing and decoded lengths, not what the
  equaliser or a track change sounds like.

### Checking by hand with sanitizers

    rm -f build/linux/*.o
    make CFLAGS="-g -O1 -fsanitize=address,undefined" LDFLAGS="-fsanitize=address,undefined"

Delete the objects again before a normal build. miniaudio reports one
harmless "left shift of negative value"; anything else is ours.

## 11. Publishing

The project is meant to live in its own GitHub repository, with this folder
as the repository root (the Makefile at the top level).

**Tests on every push** (`.github/workflows/test.yml`). Builds Linux, both
Windows targets, the installers and the packages on GitHub's Ubuntu
machines, runs the unit tests, and keeps `build/dist/` from each run as a
downloadable artifact. A second job runs the end-to-end GUI test under a
virtual display with a small window manager. The audio test runs with `AUDIO_TEST_ENV=ASAN_OPTIONS=detect_leaks=0`
because the build machine has no sound server (see the Makefile).

**The website** (`.github/workflows/pages.yml`) is the `website/` folder,
published to GitHub Pages whenever it changes. One-time setup:

1. In the repository: Settings, Pages, "Build and deployment", Source:
   "GitHub Actions".
2. At the DNS provider for `cr.rs`: a CNAME record for `amplitude` pointing
   to `<github-user>.github.io`.
3. Back in Settings, Pages: enter `amplitude.cr.rs` as the custom domain
   (it matches `website/CNAME`) and, once the certificate has been issued,
   tick "Enforce HTTPS".

**A release**, by hand: commit, set `VERSION` and `RELEASE_DATE` in the
Makefile, run `make dist`, create a GitHub Release whose tag is the
version number with a "v" in front (`v0.2.0`) and attach the seven files
from `build/dist/`. Then change the version in the download buttons of
`website/index.html`, whose addresses have the form
`https://github.com/srrudic/Amplitude/releases/download/<tag>/<file>`.

## 12. Known gaps

Not implemented:

- Windowshade mode, always on top, unfocused title bars, shaped windows
  (`region.txt`), skin cursors
- Playlist: drag to reorder, sorting, the SEL/MISC/LIST buttons, `.pls`
  files, the mini transport at the bottom, background tag reading
- Saving user equaliser presets; WinAmp's per-song AUTO presets
- Internet radio, ReplayGain, output device selection; output is always
  44.1 kHz 16-bit stereo
- WMA, ALAC, WavPack, Musepack, APE, MIDI, audio CDs
- Media keys, global hotkeys, MPRIS
- macOS backend; native Wayland (it runs through XWayland)
- Typing characters outside the system code page into the jump-to-file box
  on Windows
- Fonts for CJK, Arabic and right-to-left text

Known limitations:

- MP3 encoder padding is not trimmed, so MP3-to-MP3 changes can have a few
  milliseconds of silence.
- The displayed bitrate is file size divided by length.
- Long MP3s are slow to open because the length is found by scanning.
- On Wayland desktops, clicking a native Wayland window does not close an
  open popup menu.
- Old tags marked Latin-1 but written in a local code page show wrong
  letters.
- Settings are saved only on a clean exit.

Before a public release:

- Run and fix the Windows build on real XP and 98 systems.
- Ship the licence texts of the bundled libraries with every binary.
- Add a Debian copyright file and changelog to the package.
- Check the name "Amplitude" for trademark conflicts.

## 13. Recipes

**Add a file format.** Write `src/codec_xyz.c` with a
`codec_open_xyz(path, Codec *)` that fills the `Codec` struct, declare it in
`codec.h`, detect the format in `codec_open` (`codec.c`), and add the file
to `COMMON_SRC` and any library sources to `TP_SRC` in the `Makefile`. Then
add the extension to `is_audio_file` in `main.c`, the Windows file dialog
filter, and the MIME types in `packaging/amplitude.desktop`. Add tag support
in `tags.c` if the format has its own.

**Add a button or control.** Add a `UI_*` id in `ui.h`, its rectangle and
drawing in the window's `ui_*.c`, its artwork in the matching `paint_*`
function of `skin_default.c` (at the classic sheet coordinates, so classic
skins line up), and its behaviour in `do_action` in `main.c`.

**Add a menu entry.** Add a `CMD_*` id, a `menu_add` line in `open_menu`,
and a case in `menu_command` or `do_action`.

**Add a setting.** Add a field to `Config`, a row in the `ints` table and a
`fprintf` in `config.c`, then copy it in `apply_config` and
`collect_config` in `main.c`.

**Add a platform.** Implement every function in `platform.h` in a new
`platform_<name>.c` and add a block for it in the `Makefile`. miniaudio
already supports macOS audio output, so only the window layer is needed.
